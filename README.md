# ProxySelfHeal · 解决 Hiddify 等代理软件导致的 Windows 开机断网

**Windows 系统代理残留自愈补丁** —— 修复 Hiddify / Clash / v2rayN / Shadowsocks / sing-box 等代理软件**未正常退出就关机**后，下次开机出现 **「网络已连接，但所有网页打不开」** 的问题。

```
Windows 10 / 11 · .NET Framework 4.x · 单文件 exe · 无需管理员权限 · 仅本地连通性探测
```

> **v2.0.0 更新（重要）**
>
> v1.0 只在登录后做事——如果代理软件自己启动了、端口也活着，但**根本没连上节点**，v1 会误判为「正常」直接放过，开机照样上不了网。
>
> v2.0 改成双保险，并在关机这一侧彻底堵死：
>
> 1. **关机/重启/注销前主动清理**：常驻守护监听系统会话结束事件，先结束代理客户端，再关闭系统代理，确保下次开机时系统代理处于关闭状态；
> 2. **出网可用性探测**：端口在监听但经该代理访问外网失败（连续两次确认），同样判定为故障并复位；
> 3. **精确进程白名单**：只结束名单内的代理客户端，绝不触碰任何系统服务。
>
> v1.0 用户直接运行新版 exe 覆盖安装即可，自启项会自动升级。

## 一、问题：Hiddify 关机后，开机就断网

这是代理软件用户的高频故障，典型描述是这样的：

> 用 Hiddify 上着网，直接关机没退出程序。第二天开机，Wi-Fi 显示已连接，微信提示网络异常，浏览器所有网页都打不开。必须重新启动一次 Hiddify 才能恢复上网。

如果你遇到的是这个现象，本工具就是为你准备的。

**受影响的软件**（只要是"系统代理"模式的桌面客户端都可能中招）：

| 软件 | 是否常见 |
|---|---|
| Hiddify / Hiddify Next | 非常常见，尤其是 MSIX 商店版本 |
| Clash for Windows / Clash Verge | 常见 |
| v2rayN / v2rayNG(桌面) | 常见 |
| Shadowsocks / ShadowsocksR | 常见（老问题，教程一堆） |
| sing-box / NekoRay / NekoBox | 常见 |

## 二、根因：不是 Windows 的锅，但 Windows 也没帮上忙

这类客户端通过修改注册表接管系统流量：

```
HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings
    ProxyEnable = 1
    ProxyServer = 127.0.0.1:12334        ← 客户端自己的本地监听端口
```

问题出在三个环节的叠加：

1. **注册表是持久化的**。进程退出后这两项**不会自动消失**。
2. **回滚靠客户端自己**。正常退出时，客户端会主动把 `ProxyEnable` 改回 `0`；但这一步是**业务代码里的逻辑**，不是系统兜底。
3. **关机不给它时间**。关机时 Windows 向程序发送 `WM_QUERYENDSESSION`，若在 `HungAppTimeout`（默认 **5 秒**）内没有响应完，直接 `TerminateProcess` 强制结束。此时 `ProxyEnable=1` 已经落盘，而回滚代码根本没执行到。

于是下次开机：

- Windows **按设计原样读取**注册表 —— 它从不主动重置代理配置（代理本来就是用户的持久设置，系统没有理由清空）；
- 代理开关仍然是开的，指向 `127.0.0.1:12334`；
- 而 Hiddify 没有启动，**这个端口无人监听**，所有请求连接被直接拒绝；
- 结果就是「网络正常但网页全打不开」。而重启一次 Hiddify，它重新监听端口并重写配置，立刻恢复。

> 为什么有的软件还能联网？因为 `ProxyEnable` 只影响 **WinINET** 这一层（浏览器、Office、多数桌面客户端）。走 `WinHTTP` 或原始 socket 的程序不受影响，所以表现为"部分软件能上、部分不能"，很容易被误判成 DNS 或网卡故障。

**结论**：这不是 Windows 的 bug，也不是用户操作错误，而是「用户态代理客户端 + 无服务托管 + 关机强制终止」三者叠加的**结构性缺口**，责任在软件侧。上游短期内不会修，所以需要一层外部兜底。

## 三、解决：关机前先清理，登录后再体检

`ProxySelfHeal` 从两头下手，缺一不可。

### 第一道：关机/重启/注销前主动清理（v2.0 新增）

一个常驻守护进程监听 Windows 的会话结束事件（`WM_QUERYENDSESSION`）。在你点「关机」「重启」或「注销」的瞬间，它抢在系统强制结束进程之前做两件事：

1. 按**精确进程名白名单**结束代理客户端（先请求正常关闭，超时再强制结束）；
2. 把系统代理置为关闭并删除 `ProxyServer`，随后复查一次，防止客户端退出过程中把配置写回。

结果：**下次开机时系统代理本来就是关闭的**，指向死端口的配置根本不会存在，从源头消除开机断网。

### 第二道：登录后自动体检（兜底）

登录后延迟 25 秒检查一次系统代理。若发现异常（死端口残留、端口活着但出不了网），自动复位。最长重试 3 次、间隔 12 秒，避免误清正在启动中的代理程序。

### 判定规则

| 检测到的状态 | 动作 |
|---|---|
| `ProxyEnable=1` + 指向本机回环端口 + 该端口**不可达** | **故障态** → 置 `ProxyEnable=0`，删除 `ProxyServer` |
| `ProxyEnable=1` + 端口在监听，但**经该代理访问外网失败** | **失效态**（v2.0 新增）→ 结束代理进程后置 `ProxyEnable=0`，删除 `ProxyServer` |
| `ProxyEnable=0` + `ProxyServer` 仍留有回环死地址 | **残留态** → 仅删除脏值（不影响上网，属卫生清理） |
| `AutoConfigURL`（PAC）指向回环死端口 | 删除失效 PAC |
| 代理端口**在监听且经其确实能出网** | 判定为正常，**不做任何修改** |
| 整机本身就没有网络（直连探测失败） | 不归咎于代理配置，**不动** |
| 远程代理 / 公司内网代理 / 公网 PAC | **完全不碰** |
| `ProxyEnable=1` 但 `ProxyServer` 为空 | 判定为正常（系统会直连），不动 |

修复后调用 WinINET 的 `InternetSetOption`（`INTERNET_OPTION_SETTINGS_CHANGED` + `INTERNET_OPTION_REFRESH`）通知系统重载配置，**无需重启浏览器、无需重启资源管理器、无需重启电脑**。

## 四、快速开始

### 方式一：下载即用（推荐）

1. 到 [Releases](https://github.com/jaja1620/win-proxy-selfheal/releases) 下载 `ProxySelfHeal.exe`
2. **双击运行**，看到「部署完成」即可
3. 结束

支持单文件绿色运行，不写系统目录，不装服务，不改 PATH。

### 方式二：命令行

```cmd
ProxySelfHeal.exe --install
```

### 部署后发生了什么

只有四处改动，全部在当前用户范围内，**不需要管理员权限**：

| 动作 | 位置 |
|---|---|
| 复制程序 | `%LOCALAPPDATA%\ProxySelfHeal\ProxySelfHeal.exe` |
| 注册登录自检 | `HKCU\Software\Microsoft\Windows\CurrentVersion\Run\ProxySelfHeal` |
| 注册关机清理守护 | `HKCU\Software\Microsoft\Windows\CurrentVersion\Run\ProxySelfHealGuard` |
| 生成卸载入口 | `%LOCALAPPDATA%\ProxySelfHeal\uninstall.cmd` |

部署时会立即拉起守护进程（无需重新登录即生效），并执行一次自检、打印当前代理状态。

### 验证是否生效

```cmd
ProxySelfHeal.exe --status
```

正常态输出：

```
=== 系统代理现状 (HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings) ===
  ProxyEnable   : 0
  ProxyServer   : (空)
  ProxyOverride : <-loopback>;<local>;localhost;*.local;127.*;...
  AutoConfigURL : (空)

=== 本机回环代理端口连通性 ===
  未发现指向本机回环地址的代理端口

=== 出网链路探测 ===
  直连探测: 可用

=== 判定结果 ===
  正常: 未发现代理残留、死端口或失效代理
  登录自愈      : 已安装 (登录时自动自检)
  关机清理守护  : 已安装 (关机/重启前清理代理)
  守护进程状态  : 运行中
```

故障态会明确指出问题。**端口死了**（v1.0 就能识别）：

```
  http=127.0.0.1:12334  ->  不可达 (连接被拒绝)
  故障态: 系统代理已启用，但其指向的本机端口无人监听 —— 当前浏览器将无法上网
```

**端口活着但出不了网**（v2.0 新增识别，也是很多人的真实情况）：

```
  127.0.0.1:12334  ->  可达 (有程序在监听)

=== 出网链路探测 ===
  直连探测: 可用
  经代理探测: 不可用 (127.0.0.1:12334 端口在监听，但经该代理无法访问外网)

=== 判定结果 ===
  故障态: 代理端口在监听但不能出网（代理软件已启动但未连通节点）—— 当前浏览器将无法上网
```

### 已经断网了，想立刻恢复

```cmd
ProxySelfHeal.exe --heal --delay 0
```

## 六、安全性设计

本工具刻意把权限和影响面压到最小，以下都是硬约束：

1. **只处理本机回环地址**（`127.0.0.1` / `localhost` / `::1`）。远程代理、公司内网代理、PAC 服务器一律不碰。
2. **只处理确实不可用的代理**。端口在监听且经其能正常出网 → 判定正常、完全不动；整机本身就没网（直连探测失败）→ 不归咎于代理配置，同样不动。
3. **不误伤正在启动的代理程序**。登录后默认等待 **25 秒** 再判定，最多重试 **3 次**（间隔 12 秒）。出网可用性判定需**连续两次探测失败**才成立，避免网络抖动误清。关机清理只在系统会话结束事件中触发，正常运行期间不动作。
4. **进程处置严格按白名单**。只结束以下进程名的客户端，且跳过名称含 `service` 的进程（服务一律不碰）：

   ```
   Hiddify  HiddifyNext  HiddifyCli  HiddifyCore
   clash-verge  clash-meta  clash-win64  Clash for Windows  mihomo
   v2rayN  v2ray  xray
   Shadowsocks  ShadowsocksR  ss-local  ss-local-win
   sing-box  NekoRay  NekoBox  Qv2ray
   ```

   处置顺序为「先请求正常关闭 → 等 900 ms → 仍在则强制结束」，让客户端有机会自己回滚代理配置。

5. **只写 HKCU**。不触碰 HKLM、系统服务、内核驱动、路由表、防火墙。
6. **不需要管理员权限**，不提权、不弹 UAC。
7. **联网行为仅限出网可用性探测**。判定代理是否真能上网时，会通过代理和直连分别访问以下 HTTP 探测点（读取 HTTP 状态码，不发送任何用户数据）：

   ```
   http://connect.rom.miui.com/generate_204
   http://www.baidu.com/
   http://wifi.vivo.com.cn/generate_204
   ```

   除此之外不联网、不上报、不下载、无遥测。不需要该功能可只用 `--no-assist`／不部署，或直接查看源码。

8. **可审计**。每次动作（含被清理的原值、被结束的进程）都写日志：

```
%LOCALAPPDATA%\ProxySelfHeal\selfheal.log
```

（超过 256 KB 自动截断保留最近 300 行）

## 九、适用范围与限制

**支持**：Windows 10 / 11（含 Server 2019+），x64 / x86，.NET Framework 4.x（Win10 1809 起系统自带）。

**不覆盖**：

1. 仅处理 **WinINET 层**（浏览器、Office、多数桌面客户端）。`netsh winhttp` 层与环境变量 `http_proxy` 不在处理范围（这两层通常不会被代理客户端写入）。
2. 仅作用于**当前用户**。多用户共用机器需各自部署一次。
3. 这是**故障后自愈**，不是预防。

## 十、想从根源避免？

比"残留后修复"更彻底的做法是让代理软件改用 **TUN / 虚拟网卡模式**：

- 通过虚拟网卡 + 路由表接管流量，**完全不写注册表代理**；
- 进程消失后路由自动撤销，内核驱动随之卸载；
- 不存在"指向死端口"的持久化状态，天然免疫本类故障。

代价是需要管理员权限、需要安装虚拟网卡驱动（如 wintun），且**多款代理软件不要同时开启 TUN**（会抢路由）。

如果因为某些原因必须使用系统代理模式，那就留着本工具做兜底。

## 十一、FAQ

**Q：会不会把我正常使用的代理关掉？**
不会。判定前提是「端口不可达」。代理程序在运行时端口是活的，工具会直接判定为正常，不做任何修改。

**Q：会不会修改我的公司代理设置？**
不会。只处理指向 `127.0.0.1` / `localhost` / `::1` 的地址，远程代理一律跳过。

**Q：为什么不用计划任务，而用 Run 键？**
Run 键在当前用户登录时触发，无需管理员权限，部署体验更轻。计划任务（尤其 `ONLOGON`）通常需要提权，对分发不友好。

**Q：会不会和 Clash 之类的软件冲突？**
不会。它只读取并复位"指向死端口"的残留，不驻留、不接管流量、不监听任何端口。

**Q：日志里的"无需处理"是正常的吗？**
正常。说明当前系统代理指向的端口是活的，或原本就没有残留。
